# Architecture

The interface and product flow live in React/TypeScript. Rust is a thin local native layer inside the Tauri process; there is no AIDOO server and no separate backend to operate.

The React composition root in `App.tsx` owns bootstrap state and navigation. Product screens live in `pages/`, reusable view sections in `components/`, lifecycle ownership in `hooks/`, and pure presentation rules in `lib/`. `event-scope.ts` is the single interface for native subscriptions: it releases established listeners and listeners whose asynchronous registration completes after unmount.

The native composition root in `lib.rs` owns process setup and shared state. `app_ui.rs` owns tray, menu, overlay and localized native status; `dictation.rs` owns the recording state machine and operation lock; `recovery.rs` owns finalization and retry safety; and `commands.rs` owns the Tauri command interface, local-file authorization and diagnostics. Device and external adapters remain isolated in `audio.rs`, `shortcuts.rs`, `storage.rs`, `text_insertion.rs` and `transcription.rs`. Source layout validation keeps each code file at or below 1,000 lines so a module stays reviewable as a whole.

`AppSettings` is the persisted product contract. It is normalized whenever it is loaded or saved. The API key is deliberately excluded and lives in macOS Keychain under service `app.aidoo.whisper-lite`; every in-memory owned copy is zeroized when dropped. `storage.rs` owns atomic JSON writes, a bounded 10-item history, diagnostics redaction and failed-recording recovery. Private JSON reads are size-bounded; malformed or oversized settings, history and recovery metadata are atomically preserved as permission-restricted `.corrupt-…` files before safe defaults or audio-based recovery are used. Newly saved FLAC/TXT files and their temporary publication files use current-user-only permissions. Current output filenames use a twelve-character random identifier; legacy six-character filenames remain readable.

The recording state machine is:

`idle → starting → recording → transcribing → done/error → idle`

Voice activation is an opt-in local path beside the keyboard shortcut. `wake_word.rs` owns the pinned `livekit-wakeword` runtime, selected-microphone capture, two-second memory-only PCM ring and classifier calls. `wake_runtime.rs` owns macOS sleep/wake recovery, the acknowledgement sound and detector events. The bundled `hey_aidoo.onnx` classifier is resolved as an application resource. Before detection, audio is neither written to disk nor sent over the network. A successful detection stops the wake listener before the normal recorder acquires the microphone, marks the recording as voice-started and shows the same overlay. Voice-started recordings can stop after 1.5 seconds of silence; if no post-trigger speech is heard for five seconds, the temporary recording is deleted without an OpenAI request. Shortcut-started recordings keep their existing key-up behavior. The wake listener runs only while the app is otherwise ready and idle, and is stopped during settings mutations, microphone tests, shortcut capture, recording, transcription, recovery and sleep.

The keyboard-only native shortcut listener begins recording on key-down and requests transcription on key-up. A generation-bound five-minute watchdog stops and transcribes an unchanged active recording if key-up is lost; it cannot stop a later recording. Recording produces a temporary mono WAV. The app converts it to FLAC before upload. Temporary audio is permissioned for the current user only; partial FLAC output is removed after a conversion failure, and exact app-owned UUID temporary files left by a crash are removed after 24 hours. Recovery and user-selected output files are never part of that cleanup. Before any request can reach OpenAI, the app places the request audio in Recovery under a non-retryable filename and persists that fail-safe state. History retranscription uses a private Recovery copy and never moves or deletes the user's original FLAC. A process exit during request construction, upload, server processing or response handling therefore restarts with a visible Delete-only item instead of offering a request that might create a second charge. Recovery filenames encode whether another API request is safe. If the metadata file is absent, corrupt or could not be written, startup finds the newest exact app-owned Recovery audio file and recreates its visible state. Unknown legacy files are conservatively non-retryable to avoid a duplicate API charge. Only a failure proven safe to retry atomically renames the Recovery file back to its retryable state; a same-directory rename is required so conflicting retryable and non-retryable copies cannot survive together. A retry converts a retained WAV to a temporary FLAC while preserving the Recovery source until the whole operation succeeds. A successful result is copied to the clipboard first, then optionally written as FLAC/TXT and committed to history, and finally optionally pasted. If any local finalization step fails after OpenAI has returned text, including during explicit retranscription from history, the completed text is retained in private Recovery metadata while the audio filename remains fail-safe. A timeout or transport failure after a request may have started, an HTTP 5xx response, or an unreadable HTTP 2xx response stays non-retryable because OpenAI processing and billing cannot be ruled out. Clear client-side API rejections and failures proven to occur before the request become retryable. The visible “Finish locally” action retries only clipboard, FLAC, TXT and history work and never calls OpenAI again. A pending Recovery item blocks another transcription from history so it cannot be overwritten. Recovery cleanup first persists the charged/non-retryable state and keeps a visible Delete-only item if the audio cannot be removed.

The overlay receives state snapshots, progress events and user notices. It never owns recording state. Native events update it immediately, while a bounded authoritative snapshot poll repairs events missed when macOS wakes or resumes the hidden WebView; the poll runs quickly only during an active state and drops to a five-second idle interval. The overlay is centered in the active display's macOS work area, just above the Dock, and grows vertically so long status and error text can wrap. Status and errors are exposed as restrained VoiceOver live regions without announcing every upload-percentage change. The interface uses the macOS system font stack, the HIG 13-point default and 10-point minimum, visible keyboard focus, and system-aware Reduce Motion, Reduce Transparency and Increase Contrast styles. Onboarding and deletion dialogs trap keyboard focus, support Escape and restore the previous focus when closed. Readiness requires completed onboarding, an available Keychain key, at least one microphone, Accessibility and no retained failed recording; the main window refreshes this system state when it regains focus. Closing the main window hides it while the tray and global shortcut remain active. A retained failed recording keeps the menu bar in its action-required state until retry or deletion resolves it. A failed automatic paste keeps the exact clipboard fallback available as the menu bar's last error after its toast disappears. A macOS Reopen event restores the main window from the Dock; Quit remains explicit in the menu bar and is blocked while a native operation owns recording, transcription, key validation, microphone probing or shortcut capture so unfinished user work cannot be discarded.

AIDOO Control keeps a memory-only cursor over the most recent patient search. One unique result is selected automatically; an explicit selection or “next patient” moves the cursor and presents that patient's record. The direct clinical protocol opens `mode=status` when status entry begins, writes and independently reads back every interpreted status without a second confirmation round trip, and refreshes the same view after every attempt. “Save status” then presents `mode=treatment`; diagnosis, procedure and official-note commands resolve the current server catalogs, write directly only when the patient, tooth and treatment row are unambiguous, read the result back and refresh Treatment. Ambiguous patients, missing visit funding and multiple treatment rows remain spoken clarification points. Schedule discovery reads the selected doctor's weekly work intervals and the requested appointment range, excludes every doctor or room overlap in 15-minute increments, stores one opaque proposed slot in memory, and opens the schedule on its exact date and doctor. An explicit booking command resolves one patient, rechecks occupancy, issues one create request, performs an independent read-back, and refreshes the same schedule; ambiguous writes are never retried. A short cache-busting query makes the deployed AIDOO frontend reload its server state. On macOS the native layer first reuses an existing Google Chrome tab for the configured clinic through Apple Events. If that permission is unavailable it opens the canonical URL in Chrome, then falls back to the default browser. Patient identifiers, search results, schedule slots and URLs are never written to diagnostics or persisted as clinical context.

Microphone routing follows the selected device, then the current system default, then the remaining available inputs when automatic fallback is enabled. A non-primary input is reported as a fallback even when automatic system-default selection is used. With fallback disabled, only the selected device is attempted. Calls into the dedicated audio worker have a 30-second deadline: a timed-out start queues an unconditional stop, and a late completed capture removes its temporary WAV automatically when no caller receives it. API-key validation, microphone tests and history/recovery deletion share the native operation lock with recording and transcription. Settings and onboarding controls disable while dictation is active, and settings or shortcut-capture mutations are also rejected by the native operation lock.

The WebView CSP permits local packaged scripts, styles, images and Tauri IPC; it blocks objects, frames, forms and base-URL changes. OpenAI communication is implemented in native code and targets `api.openai.com`. Tauri capabilities and application commands are split per window: the main window alone can use settings, recording, local files, Launch at Login and the two exact external destinations: the OpenAI API-key page and `mailto:support@aidoo.bg`. The overlay can only read its reduced bootstrap state and current recording state, listen for native events, resize itself and request native repositioning; its bootstrap payload contains no history, API-key status, microphone inventory or local paths. API validation uses `GET /v1/models`; an authentication failure is rejected, while an authenticated `403 Forbidden` is accepted so an endpoint-restricted key that can transcribe does not fail onboarding merely because it cannot list models. Transcription uses `POST /v1/audio/transcriptions`. Audio is streamed from disk into the request and network calls have bounded connection and total timeouts. Both clients accept HTTPS only and reject redirects, keeping bearer credentials on the fixed OpenAI request paths. Incoming transcription JSON is limited to two megabytes; API error bodies are limited to 64 kilobytes and their displayed message is normalized to 500 characters. No analytics or background telemetry exists. A user-requested diagnostic ZIP contains sanitized app logs, settings without the API key or local device paths, basic system/version data and up to three relevant Apple crash reports. At most one megabyte is read from each report. OpenAI-style keys, the home-directory path and transcript text known to the local history are redacted from included text. The ZIP is written to a private temporary file, synchronized and atomically published only when complete; only files in the private data directory with the exact generated diagnostic filename format can be reopened through the app. Quit remains blocked during creation. The package remains local until the user reviews it and chooses whether to attach it to an email to AIDOO support.

The Live WebRTC data channel exposes final delegated Responses events to the main window. For each unique response ID, the native usage ledger validates and persists the reported input, cached-input, cache-write and output token counts, then prices them against the fixed `gpt-5.6-terra` rates. Duplicate events cannot add the same response twice, and existing usage files migrate through serde defaults. Only token counts, model ID, timestamp and calculated cost are stored; prompts, tool arguments, tool outputs and patient data are excluded.

Releases contain a notarized and stapled DMG plus its SHA-256 checksum. New versions are published on the AIDOO website and installed manually; the application has no updater endpoint or background version check. The release verifier rejects updater dependencies and any native HTTPS destination outside the two required OpenAI API endpoints.

The macOS bundle uses English as its base `Info.plist` language and ships `en.lproj` and `bg.lproj` `InfoPlist.strings` resources. This keeps the system Microphone permission explanation aligned with the user's macOS language before the WebView interface is available.
